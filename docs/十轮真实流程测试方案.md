# Bond 邮件 Agent · 十轮真实流程测试方案

**目的**：用真实邮箱往来验证系统在真实环境下的完整业务流程，覆盖自动回复、人工审批、去重、频控、隔离、异常处理等全部关键路径。

**测试方式**：你（或同事）用一个测试邮箱（如 2656277828@qq.com）扮演「Bond 代理商业务员」，收到系统询价邮件后按本方案回信。系统侧全程只通过网页审核台操作。

---

## 〇、测试前准备（一次性）

| # | 准备项 | 怎么做 |
| --- | --- | --- |
| 1 | 系统服务运行 | 确认 http://127.0.0.1:8787 可打开，看板显示「邮件守护」运行中 |
| 2 | 委托公司就绪 | 「发起询价」页第 1 步确认至少 1 家公司状态为「可发起询价」（三份文件 ✓） |
| 3 | 代理商档案 | 每轮测试前在用到的代理商档案里确认邮箱为测试邮箱（QQ 邮箱）；每轮用**不同代理商**，避免频控互相干扰 |
| 4 | 自动模式 | 看板 → 对应 Case → 自动模式设为 `on`（自动发送） |
| 5 | 通知渠道 | 飞书群机器人可用（收到 Invoice 会推群） |
| 6 | 回信方式 | **必须在收到系统邮件后点「回复」**（保留原主题中的 BOND-2026-XXXX 编号），不要另起新邮件 |

**回信附件命名规则**（系统按文件名识别）：
- Bond 文件 → 文件名含 `bond`，如 `bond.pdf`
- 发票 → 文件名含 `invoice`，如 `invoice.pdf`

## 一、通用回信模板（扮演代理商时复制改参数）

**T1 报价信**
> 主题：Re:（原主题不动）
>
> Hello,
>
> Thank you for your inquiry. For the bond request, our quote is **$750.00** for the first year.
> Payment by wire or Zelle. Looking forward to your confirmation.
>
> Best regards, A1 Surety

**T2 索要申请材料**
> 主题：Re:（原主题不动）
>
> Hi, before we can issue the bond, please provide the application documents:
> articles of organization, EIN letter, and ID of the legal representative.

**T3 Bond 文件交付**（附件：bond.pdf）
> 主题：Re:（原主题不动）
>
> Hi, please find attached the executed bond. Thank you for your business.

**T4 发票/付款信息**（附件：invoice.pdf）
> 主题：Re:（原主题不动）
>
> Hi, attached is our invoice #1042.
> Amount: $750.00, due 2026-12-01, payment by Zelle to ms Bond.
> Please remit payment at your earliest convenience.

## 二、十轮测试场景

### 场景 1：标准全流程（核心验收）

| 项 | 内容 |
| --- | --- |
| 目的 | 验证最常见路径全自动化：询价 → 报价 → 确认 → 材料 → Bond → 发票 → 付款通知 |
| 前置 | 代理商 A（测试邮箱），委托公司 1，模式 on |
| 步骤 | ① 审核台发起询价（勾选直接发送）② 收到询价后回 T1（报价 $750）③ 收到自动确认后回 T2 ④ 收到材料自动回复后回 T3（附 bond.pdf）⑤ 收到 Bond 确认后回 T4（附 invoice.pdf，发票号 1042，$750）⑥ 飞书群收到付款通知后，审核台回填付款方式与流水号 |
| 预期 | ②③④⑤ 每一步系统在 ~30 秒内自动回复，**全程无需人工**；⑤ 飞书推送含金额/发票号/付款方式；⑥ 案件状态走到「已付款」 |
| 验证点 | 看板状态徽章每步变化正确；Case 详情进度条逐步点亮；审计无 blocked 记录 |

### 场景 2：超审批线报价（人工介入）

| 项 | 内容 |
| --- | --- |
| 目的 | 验证 >$1,000 报价不自动确认，进入人工审核 |
| 前置 | 代理商 B，委托公司 1，模式 on |
| 步骤 | ① 发起询价 ② 回 T1，但金额改为 **$1,250** ③ 观察系统动作 → 审核台找到待审草稿，点「批准」④ 批准后回 T2，走完后续（T3 → T4，金额 $1,250）|
| 预期 | ② 系统不自动确认，草稿状态为待审且说明原因（超审批线）；③ 批准后正常发出；④ 案件闭环 |
| 验证点 | 草稿页能看到闸门提示；批准记录有审核人；飞书推送金额为 1250.00 |

### 场景 3：无关回复（意图识别容错）

| 项 | 内容 |
| --- | --- |
| 目的 | 验证系统对无法识别的回复不乱动作 |
| 前置 | 代理商 C，委托公司 1，模式 on |
| 步骤 | ① 发起询价 ② 回复一句无关内容："OK thanks, I will check tomorrow."（不含报价/材料/Bond/发票关键词）③ 等待观察 ④ 再回 T1 正常报价，走完流程 |
| 预期 | ② 系统不自动回复（或生成待审草稿且意图为 unclear），案件状态不变、不发错信；④ 恢复正常自动流程 |
| 验证点 | 审计中该消息 decision 为 unclear；未产生错误草稿或错误状态推进 |

### 场景 4：重复发票去重

| 项 | 内容 |
| --- | --- |
| 目的 | 验证同一张发票不会重复推群、不会安排两次付款 |
| 前置 | 代理商 A，新开一个流程走到场景 1 的第 ⑤ 步（发票号 1042 已推送过一次）|
| 步骤 | ① 再回一封一模一样的 T4（同发票号 1042，同附件）② 观察飞书群和数据库 |
| 预期 | 飞书**不出现第二条** 1042 的付款通知；Invoice 表不新增记录；案件状态保持 invoiced 不回退 |
| 验证点 | 审计里第二封邮件标记为 duplicate/未重复通知 |

### 场景 5：频控限流（一小时内频繁往来）

| 项 | 内容 |
| --- | --- |
| 目的 | 验证 3 封/小时/代理商 的频控生效，防止骚扰代理商 |
| 前置 | 代理商 C，委托公司 1，模式 on；一小时内已自动发出 2 封（询价 + 确认）|
| 步骤 | ① 快速连续回 T2（要材料）→ T3（bond.pdf）→ T4（invoice.pdf），间隔 1 分钟内 ② 观察第三封的处理结果 ③ 等 1 小时后到审核台批准被限流的草稿 |
| 预期 | 第 3 封自动回复被频控拦截，落为「已阻塞」草稿而非直接发送；人工批准后可发出 |
| 验证点 | 草稿 blocked 原因包含频控规则 ID；批准后出站台账有记录 |

### 场景 6：双委托并行隔离

| 项 | 内容 |
| --- | --- |
| 目的 | 验证两家公司同时进行时，回复串户不会发生（防串户是红线）|
| 前置 | 委托公司 1 与委托公司 2 均「可发起询价」；代理商 A、B 都指向测试邮箱 |
| 步骤 | ① 公司 1 × 代理商 A、公司 2 × 代理商 B 同时发起询价 ② 交替回复两条线程：A 线程回 T1（$750）、B 线程回 T1（$680）③ 各自走完后续 |
| 预期 | 两条线程报价、材料、Bond、发票全程互不混淆；两个案件状态各自独立推进；飞书推送的委托公司名与金额一一对应 |
| 验证点 | 看板两个案件并行推进；草稿正文中的公司名与线程一致 |

### 场景 7：异常价提示

| 项 | 内容 |
| --- | --- |
| 目的 | 验证报价明显高于基准时给出提示但不阻断 |
| 前置 | 委托公司 2 已在场景 6 收到正常报价 $680（或先造一个基准价）|
| 步骤 | ① 委托公司 2 × 代理商 C 发起询价 ② 回 T1，金额改为 **$1,000** 以内但明显偏高（如 $980，≥ 基准 1.3 倍）③ 观察 |
| 预期 | 系统照常推进（≤$1,000 自动接受），但看板/案件页出现异常价提示，不静默放过 |
| 验证点 | 提示为 notices 类（不改变动作）；审计有异常价记录 |

### 场景 8：发票 PDF 字段提取

| 项 | 内容 |
| --- | --- |
| 目的 | 验证从 PDF 提取发票号/金额/到期日/付款方式，而不是依赖正文 |
| 前置 | 制作 invoice.pdf：正文只写 "Please see attached invoice."，金额、发票号（如 #2044）、到期日、ACH 付款信息全部只写在 PDF 里 |
| 步骤 | ① 场景流程走到 Bond 交付后 ② 回 T4 变体：正文无金额，附 invoice.pdf ③ 查看飞书推送 |
| 预期 | 推送金额、发票号、到期日、付款方式与 PDF 内容一致（即使正文一个数字都没有）|
| 验证点 | Invoice 记录字段完整；推送中的「汇款要素」与 PDF 相符 |

### 场景 9：状态错序回复（乱序容错）

| 项 | 内容 |
| --- | --- |
| 目的 | 验证代理商提前发来发票/先发 Bond 后又改报价等错序情况不会打乱状态机 |
| 前置 | 代理商 B，流程进行到「已索取材料」（T2 已发）|
| 步骤 | ① 跳过材料环节，直接回 T4 发票（金额 $900，发票号 3001）② 再回 T1 报价 $500 ③ 最后回 T3（bond.pdf）补流程 |
| 预期 | ① 系统按发票处理（推送群、状态到 invoiced），不崩溃不乱发 ② 报价入库但**不自动回退状态**（已 invoiced 的案件不退回 quoted），生成待审草稿供人工判断 ③ 人工批准后续草稿，流程可走完 |
| 验证点 | 状态机无回退跳跃（除人工操作）；每一步都有审计记录 |

### 场景 10：守护中断恢复 + dry_run 安全

| 项 | 内容 |
| --- | --- |
| 目的 | 验证服务重启后流程无缝接续，以及 dry_run 模式不出信 |
| 前置 | 代理商 A，模式先设为 `dry_run` |
| 步骤 | ① 发起询价（dry_run 只出草稿不发送）② 审核台批准发送 ③ 回 T1（$750）④ **重启电脑或执行 agent.ps1 restart** ⑤ 服务恢复后回 T2，确认自动流程继续 ⑥ 把模式切回 `on`，走完剩余流程 |
| 预期 | ① 无任何邮件发出 ③ 只出待审草稿 ④⑤ 重启后 30 秒内恢复轮询，之前的线程照常自动处理 ⑥ 案件闭环 |
| 验证点 | 重启前后线程消息连续（无漏处理）；模式切换有审计记录 |

## 三、建议执行顺序

```
第 1 轮   场景 1（标准流程，先验证主链路）
第 2 轮   场景 2（人工审批）
第 3 轮   场景 3（容错）
第 4 轮   场景 4（紧跟场景 1 的同一线程做去重）
第 5 轮   场景 6（双委托并行）
第 6 轮   场景 7（紧接场景 6 的报价做异常价）
第 7 轮   场景 5（频控，注意与其他轮次间隔 1 小时）
第 8 轮   场景 8（PDF 提取）
第 9 轮   场景 9（乱序）
第 10 轮  场景 10（重启恢复，放最后）
```

## 四、每轮通用检查清单

- [ ] 每封入站邮件在看板「最近动态」有审计记录
- [ ] 系统自动回复在 30 秒内到达测试邮箱
- [ ] 案件状态徽章与预期一致（询价已发出 → 已收到报价 → … → 已付款）
- [ ] 出站内容不包含其他公司/案件的信息（无串户）
- [ ] 需要推群的场景：飞书消息内容完整、无重复
- [ ] 结束后案件状态为 paid / closed，无悬挂草稿
